> **Version:** 1.0

> **작성 경위:** code_work 루트 세션에서 조사·분석만 수행. 코드는 손대지 않음.
> **이어받을 곳:** my_store 전용 세션

## 0. 이 문서의 목적

`johunsang/smartku`(스마트스토어·쿠팡 통합관리 Tauri 앱)를 분석하고, my_store의
확장 방향(택배 프린터·택배사 연동)을 검토한 결과를 정리한다. 실행은 이 문서를 받는 세션에서 한다.

## 1. 확정된 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| **비상업 라이선스** | **제약 없음 — 코드 참조·이식 가능** | 사용자가 2026-08-14 명시: 현재 상업적 판매에 사용하지 않음. smartku는 PolyForm Noncommercial 1.0.0 |
| **배포 범위** | 혼자 운영 + 향후 소수(몇 명) 추가 활용. **대량 배포 안 함** | 사용자 확정 |
| **주 아키텍처** | **NAS Docker 웹앱 유지** | 24시간 자동화(주문 수집·재고 동기화·알림)와 폰 접근이 핵심 자산 |
| **프린터·송장** | **별도 로컬앱으로 분리해 웹앱과 연동** | 브라우저 프린터 제어의 제약(아래 3절) |
| **smartku 도입 방식** | 전면 대체·통째 사용 아님. **기능·패턴만 선별 이식** | 아키텍처 노선이 다르고 코드 구조가 부적합(4절) |

## 2. smartku 요약

- 스마트스토어·쿠팡 통합관리 **Tauri v2 + Rust + 로컬 SQLite** 데스크톱 앱
- 110 파일 / Rust 11개(1MB) / 9⭐ / 2026-07-27 생성, **2026-08-01 이후 커밋 없음**
- 프런트엔드는 `dist/index.html` **단일 파일 875KB** (바닐라 JS, 빌드 없음)

### my_store에 없는 기능

| 기능 | smartku 위치 |
|---|---|
| 쿠팡 WING API (HMAC 서명) | `markets/coupang.rs` 149KB |
| 도매매 OpenAPI 위탁 소싱 | `markets/domeme.rs` |
| 정산(매출·지급내역) 조회 | — |
| 네이버↔쿠팡 카테고리 매핑 | — |
| 해외구매대행(AGENT_BUY·통관부호·인보이스) | — |

반대로 my_store에만 있는 것: **재고 관리, 공급업체 발주, 경쟁사 벤치마킹**

### 참고할 설계 원칙 (README 명시)

1. 업무 데이터는 로컬이 원본, 클라우드는 선택적 백업
2. **주문 개인정보(`orders`)는 원격 스냅샷에서 항상 제거**
3. **마켓 API 호출 전 필수값을 먼저 검증해 잘못된 요청을 보내지 않음**
4. **파괴적 작업(일괄 변경·삭제·복원)은 미리보기 → 확인 2단계**

## 3. 웹앱 vs 데스크톱 — 검토 결과

### 프린터가 결정 축

| | 웹 (WebUSB / Web Serial) | 데스크톱 |
|---|---|---|
| 브라우저 | **Chrome·Edge 계열만** (Firefox·Safari 미지원, 전역 약 76%) | 무관 |
| iOS/iPad | **불가** (Safari 엔진 강제) | 무관 |
| 조건 | HTTPS + 사용자 제스처 + 기기 권한 승인 | 없음 |
| 제어 방식 | OS 스풀러 우회, raw ESC/POS·ZPL 직접 구현 | OS 프린터 API 사용 |

**함정:** 웹앱이 프린터를 못 쓰면 결국 로컬 에이전트를 설치하게 되고, 그 순간 배포 난이도는
데스크톱 앱과 같아진다. 다만 **혼자 쓰는 환경에서는 에이전트 하나만 깔면 되므로 웹앱 유지가 합리적.**

### 작업 성격별 분리

```
프린터·큰 화면 필요          폰에서 하고 싶은 것
├─ 송장 출력                 ├─ 주문 확인
├─ 대량 상품 등록            ├─ 재고 부족 알림
├─ 상세페이지 조립           ├─ 매출 조회
└─ 이미지 편집               └─ 발주 승인
      ↓                            ↓
   로컬앱                    NAS 웹앱 (현행 유지)
```

### 채택 구조

```
NAS (Docker)              ← 24시간 자동화 + 웹 UI + 폰 접근 (현행)
   │
   └─ 로컬앱 (사무실 PC)   ← 송장 출력 전담, 필요 시 이미지 편집까지 확장
```

향후 소수 사용자가 붙어도 이 구조가 유지된다. 각자 로컬앱만 설치하면 된다.
Tauri 경험은 `smart_category` 프로젝트에 이미 있음.

## 4. UI 벤치마크 — 우선순위

실제 데모 영상(`docs/media/smartku-promo.mp4`) 프레임과 `dist/index.html` 구조를 분석한 결과.

### ① "준비 안 됨 N" 사전 검증 뱃지 — 난이도 낮음 / 효과 즉시

상품 목록 각 행에 마켓 등록 필수값 미충족 개수를 뱃지로 표시.

```
MEWAY Durable 12oz Stainless Steel Wine Tumbler...
WEB-42294b7b7103ca5b
[구매대행] [⚠ 준비 안 됨 1]
```

등록을 시도하기 전에 목록에서 바로 보인다. 마켓 API는 실패 메시지가 불친절하고 잘못 보내면
실제 상품이 이상하게 등록되므로, 사전 검증의 가치가 크다.
**구현:** 필수 필드 체크 함수 + 뱃지 컴포넌트. 스키마 변경 불필요.

### ② 미리보기 → 확인 2단계 — 난이도 낮음 / 사고 방지

일괄 변경 시 영향 대상을 **건수가 아니라 실제 항목으로** 나열한 뒤 확인받는다.

```
상품명에 '텀블러'가 포함된 원본상품의 판매가를 5% 인상하는 작업입니다.
먼저 영향 상품 수와 변경 전·후 가격을 미리보기로 보여드리며, 확인 후에만 실제 반영됩니다.

        [ 텀블러 판매가 5% 인상 미리보기 ]      ← 1단계

⚠ 5건이 대상입니다 — 실행하려면 확인하세요
 · MEWAY 12온스 진공단열 스테인리스 와인 텀블러... (₩102,200)
 · 1.18리터 대용량 텀블러 스텐 빨대 포함... (₩6,800)
 · 테스트상품 스테인리스 텀블러 500ml 등록확인용 (₩29,900)

        [ ✓ 5건 실제 변경 ]                    ← 2단계
```

배울 점 네 가지:
- 작업 내용을 평문으로 먼저 설명하고 "확인 후에만 반영"을 명시
- 버튼 라벨에 동작을 그대로 담음 (단순 "미리보기"가 아님)
- 대상을 실제 상품명·가격으로 나열
- 최종 버튼에도 건수 재표기

**적용처:** 일괄 작업, 공급업체 발주, 가격·재고 일괄 수정

### ③ AI 제안 → 버튼 확인 경계 — 난이도 낮음 / 안전성

AI가 요청을 받아도 **바로 실행하지 않고 실행 버튼을 제시**한다.

```
내 원본상품에서 상품명에 '텀블러'가 포함된 상품을 조회해 표로 보여드릴게요.
        [ 텀블러 상품 조회 ]      ← 사용자가 눌러야 실행
```

명세서 규칙: **AI는 미리 정의된 액션만 실행. 대화를 통한 마켓 등록은 차단하고 수동 업로드 버튼 요구.**
→ 읽기·집계는 대화로, 실제 마켓에 나가는 행위는 손으로. my_store의 AI 상세페이지 생성 기능에
같은 경계를 적용할지 검토.

### ④ 로컬 상태 vs 실제 마켓 상태 비교 — 난이도 중간 / 운영 신뢰도

액션 바에 대조 전용 버튼을 둔다: `[쿠팡·스스 실제상품 조회]` `[가격·재고 비교]`

내 DB가 진실이라고 가정하지 않는다. 마켓 API는 조용히 실패하거나 값이 어긋나는 일이 잦다.
명세서: "로컬 편집과 실제 마켓 상태를 구분하고, **API 실패 시 성공 플래그를 남기지 않는다**"

### ⑤ 원본상품(마스터) 모델 — 난이도 높음(스키마) / 쿠팡 확장 시 필수

**현재 my_store 스키마 (`4_Database_Design.md`)**

```
STORES ||--o{ PRODUCTS      ← 상품이 스토어에 종속
```

**smartku 모델**

```
원본상품(마스터)
  ├─ 스마트스토어 배포 → 이름·가격·카테고리·옵션 개별 오버라이드
  └─ 쿠팡 배포        → 이름·가격·카테고리·옵션 개별 오버라이드
```

상품 1건을 원본으로 두고 마켓별 필드를 오버라이드로 관리한다
(smartku는 `data-mfield=` 속성 36개로 처리).

단일 마켓에서는 불필요하지만 **쿠팡을 추가하는 순간 반드시 필요해진다.**
나중에 넣으면 마이그레이션 비용이 크므로, 쿠팡 확장 계획이 있으면 스키마부터 결정해야 한다.

### 참고: 행 내 배포 현황 인라인 표시

```
컬럼: ☐ | 상품 | 판매가 | 재고 | 출처·판매 | 배포 현황·마켓 등록 | 관리

노르디스케 Oi Rug...   ₩99,000  0 마켓별  [coupang]  coupang_win… 07-19 05:28
14979882470                               0 판매     [판매중지][판매재개][상태확인][메시지]
[미지정] [⚠ 준비 안 됨 1]                  기본 사업자           [편집][배포▾][판매관리]
```

상세로 들어가지 않고 목록에서 판매중지·재개를 처리. 상단 계정 칩(`🟢 스스 최신 10개`
`🟣 쿠팡 최신 5개`)과 행 내 뱃지의 마켓 색상을 통일.

## 5. 따라하지 말 것

- `dist/index.html` **875KB 단일 파일** — 화면 9개 + 모달 20개 이상이 한 파일에.
  my_store의 Next.js + Radix UI 구성이 모든 면에서 우수
- `src-tauri/src/lib.rs` **14,129줄 / Tauri 커맨드 137개 / 함수 298개** —
  `~/.claude/rules/coding-style.md` 기준(800줄 max)의 17배
- **vendor 통째 내장** — `tui-image-editor.js` 1.9MB + `fabric.min.js` 305KB
- **높은 정보 밀도** — 한 행에 뱃지 4~5개. 혼자 쓸 땐 최적이나 사용자가 늘면 학습 곡선

## 6. 다음 단계

### 즉시 착수 가능 (스키마 무관)

1. `①` 준비 안 됨 뱃지 — 마켓 등록 필수값 검증 함수 + 뱃지 컴포넌트
2. `②` 미리보기 → 확인 2단계 — 일괄 작업·발주 경로부터
3. `③` AI 실행 경계 — 조회는 대화, 마켓 반영은 버튼

### 결정이 필요한 것

- **쿠팡 확장 여부** → `⑤` 원본상품 모델 도입 시점을 가른다.
  로컬앱 설계 전에 정해야 함(송장 데이터가 "어느 마켓의 어느 주문"에서 나오므로)
- **로컬앱 범위** — 송장 출력만인지, 이미지 편집·대량 등록까지 흡수할지
- **택배사 연동 방식** — 직접 API vs 중계 서비스. 고정 IP 화이트리스트 요구 여부 확인 필요
  (이 경우 NAS 서버 경유가 유리)

### 미조사 영역

- 국내 택배사 API 연동 요건 (인증 방식, IP 제한, 송장 발번 규격)
- 라벨 프린터 모델별 명령어 규격 (ZPL / ESC-POS / 제조사 SDK)
- Tauri의 프린터 접근 방식 (OS 프린터 API 경유 vs 시리얼 직접)
